# VapourSynth R75 → R82 upgrade — 2026-11-12

## Why

R82 is the current release (published 2026-11-01; R83 unreleased at time of
writing). The vendored build was pinned at R75 — seven releases behind.
Relevant upstream changes for us between R75 and R82: deadlock fixes
(r76/r77 threading, logging, synchronous getFrame), `_Range` property
(H.273) with the deprecation of `_ColorRange` for api-4.2+ filters, cache
heuristics for long cyclical patterns, C++20 toolchain requirement (we
already build C++20), Python 3.14 support in the python module, and an
API-3 removal that turned out to matter (see below).

## What changed in our pipeline

- `scripts/build-vapoursynth.sh` default tag is now **R82**.
- **Cython 3.3.1+ is required** to compile R82's `vapoursynth.pyx` under
  Python 3.14: the file references the `sentinel` builtin
  (`try: sentinel(...) except NameError`), which Cython 3.2.4 rejects at
  compile time ("undeclared name not builtin"). The script's venv upgrades
  Cython automatically (`pip install --upgrade cython`).
- **Static zimg patch (restored):** R75's tree carried
  `dependency('zimg', static: true)`; the R82 tree dropped the static
  preference, which links Homebrew's `libzimg.2.dylib` and fails the
  portable bundle's self-containment audit ("PATH POLICY"):
  `libvapoursynth.4.dylib` must not reference `/opt/homebrew`.
  `build-vapoursynth.sh` idempotently patches the cloned source back to
  `static: true` (patched source kept in `vendor/vapoursynth/src-R82/`;
  change recorded here for the LGPL correspondence trail). Verified after
  rebuild: `otool -L libvapoursynth.4.dylib` → zero zimg references.
- Dev scripts that pinned `install-R75` paths now resolve
  `vendor/vapoursynth/active` (which points at `install-R82`).

- Staged portable bundle reports the embedded runtime as

## Live finding: the SHIPPED core is R79, not R82 (2026-11-12)

While qualifying the R82 bundle with a real render, the core rejected most of
the curated plugin set:

    Warning: Plugin …/Contents/Plugins/lib….dylib uses API 3, which is no
    longer supported.

Census of the 61 staged plugins (symbol check, `VapourSynthPluginInit2`):

- **25 are API 4** — mvtools, removegrain, fmtconv, tcanny, vivtc, miscfilters,
  resize2, vszip, zsmooth, sneedif, eedi3m, descale, fft3dfilter, …
- **36 are API 3** — including **liblsmashsource (LSMAS: LWLibavSource source
  loading)**, nnedi3, bm3d, neo-f3kdb, sangnom, tcomb, …

  *Correction 2026-11-13:* masktools2 was never part of the curated set (the
  "mask" hit in symbol lists is libtedgemask). The vendored havsfunc
  self-implements its `mt_*` helpers in Python over `core.std`, so QTGMC's
  plugin dependencies are mvtools (API-4) + nnedi3 (API-3). Re-census after
  the curated-set pass: 56 plugins = 23 API-4 + 33 API-3; the API-3 list is
  in the 2026-11-13 session records.

API-3 support existed through **R79** (deprecation warnings only). **R80+ removed
it entirely** — the R82 core carries no vs3 compat layer (verified in the R79 /
R80 / R81 / R82 `vscore.cpp` sources), so re-adding it would mean re-porting
the whole compat machinery and diverging from upstream. Shipping R82 as-is
would break 36 of 61 plugins, including the QTGMC chain (masktools) and the
standalone source path (LSMAS).

**Decision: the beta ships against R79** — the newest core that runs the full
curated set. R82 remains built and staged-ready in-tree (`install-R82`, plus
the static-zimg patch, the Cython workaround, and the conditional
`libvapoursynthfilters` staging, all kept), for the day the plugin set is
migrated to API 4.

**Follow-on workstream (own project, not beta):** re-vendor the 36 API-3
plugins from current upstreams (most upstreams have since moved to API 4),
with fresh license review per component; then the core can move to the newest
release.
